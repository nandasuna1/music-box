# W1 — Design tokens, component boundaries, and visual states

## Goal

Make the app's existing dark/gold visual language consistent and reusable
without introducing a heavyweight UI framework or redesigning every screen.

## Scope and decisions

- Preserve the current dark, gold-accented visual direction and existing
  supported-platform behavior. Do not add a light-mode redesign or change
  theme-switch behavior in W1.
- Keep Expo and the current stack; do not add a UI package.
- Prefer extending `constants/theme.ts` and existing shared component patterns
  over creating a separate design-system directory or many one-off
  abstractions.
- Preserve rating, search, save, authentication, navigation, and data behavior.
  Visual migration must not introduce product behavior changes.
- Create a reusable primitive only when existing cross-screen use or a
  concrete testability benefit justifies it. Keep feature-specific components,
  such as `RatingInput`, feature-oriented.
- W1 focuses on visual consistency and component contracts. W2 owns
  screen-reader semantics and accessibility verification; W4 owns query and
  mutation reliability.

## Current-state evidence

- `constants/theme.ts` defines generic light/dark colors and fonts, but no
  semantic spacing, typography, radii, elevation, or interaction-state tokens.
- `ThemedText` provides five text variants, but most routes use raw `Text` and
  local styles. `ThemedView` only supplies a themed background.
- `RatingInput` uses hard-coded gold/gray stars and has no disabled prop.
  `SearchBar` is controlled but hard-codes a white field and exposes only
  `value` and `onChange`.
- Profile components, home, album detail/rating, and login each contain inline
  or local visual constants. Avoid broad restructuring solely for styling.
- Automated tests are concentrated in `__tests__/home.test.tsx`; there are no
  component-specific contract tests yet.

## Work

### 1. Define semantic theme tokens

- Extend `constants/theme.ts` with a compact semantic dark-surface palette,
  text and muted-text colors, accent and status colors, spacing scale,
  typography scale, radii, elevation, and interaction states (pressed,
  disabled, focused/error as presentation values).
- Preserve existing exports (`Colors`, `Fonts`) or update consumers
  coherently; do not create a competing token source.
- Check text/background and control-state contrast for the selected palette.
  Record names and values for W2 to reuse.

### 2. Agree on minimal reusable component contracts

- Define typed props and deterministic visual state behavior for primitives
  selected from confirmed cross-screen repetition.
- Buttons should have explicit variants and disabled/loading states. Text
  fields should remain controlled and expose visual error/disabled states
  without changing form behavior.
- Refine/reuse `ThemedText`, `ThemedView`, `RatingInput`, and `SearchBar` where
  appropriate instead of replacing them wholesale.
- Do not introduce an abstraction used only once without a concrete reuse or
  testability benefit.

### 3. Migrate agreed UI surfaces

- Apply tokens and shared primitives to repeated surfaces in login,
  discovery, album detail/rating, and profile.
- Replace scattered raw colors, spacing, and type values only on touched,
  agreed surfaces; preserve visual hierarchy and navigation/data interactions.
- Retain dynamic text scaling and support narrow/wide layouts. Avoid fixed
  heights that clip larger text.

### 4. Add focused tests and update documentation

- Follow a test-first workflow for new component contracts: write the
  behavior-focused test, confirm it fails before implementation, then
  implement the smallest change that makes it pass.
- Test meaningful component behavior, including controlled values/callbacks,
  disabled interaction, and loading state. Avoid snapshots as the only proof.
- Update `docs/components.md` and relevant theme/component docs with token
  names, selected primitive boundaries, and prop/state behavior.
- Coordinate token and state naming with W2, without implementing its
  accessibility inventory or screen-reader checks in W1.

### 5. Verify implementation

- Run focused component/home tests, lint, and formatting checks on changed
  files. Run the full Jest suite if shared components are imported broadly.
- Inspect representative native iOS and Android layouts at narrow and wider
  widths and with enlarged text where available. Record platform limitations
  rather than claiming unverified coverage.
- Preserve and report the known W0 repository-wide formatting failures unless
  a touched file changes their status.

## Acceptance criteria

- Repeated semantic colors, spacing, and type styles on touched surfaces use
  named tokens instead of scattered literals.
- Reusable components have typed contracts and deterministic disabled/loading
  behavior.
- Normal, pressed, disabled, loading, empty, and error states are visually
  coherent on the screens/components in scope.
- Dynamic text sizing and narrow/wide layouts remain usable on migrated
  surfaces.
- Focused component tests cover meaningful behavior and props rather than
  relying on implementation snapshots.
- Relevant component documentation is updated and accurately describes the
  code that exists.

## Dependencies and non-goals

- W0's [quality contract](quality-contract.md) is the shared definition of
  done.
- Coordinate semantic colors and interaction-state names with W2 before
  implementation. Accessibility semantics and device screen-reader evidence
  remain W2 scope.
- Avoid query/mutation behavior and Firestore contracts, which belong to W4/W5.
- Do not adopt a large design-system package, redesign all screens, restructure
  routes solely for visual consistency, or add blanket memoization.
